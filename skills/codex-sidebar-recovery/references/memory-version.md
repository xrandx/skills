# 本地记忆检查与版本切换

用于检查账号切换后本地记忆是否还在，或按用户要求切换 `memories` / `memories_v2`。此处的“迁移”指选择记忆管线，不代表复制、合并或完整迁移历史内容。

## 先区分文件存在与实际使用

1. 确认实际 Codex home 和生效的配置来源。检查 `memories/`、`memories_v2/` 的摘要与 rollout 文件是否存在；统计文件时排除 `.git`。只报告必要的数量、文件状态，不倾倒私人记忆全文。
2. 必要时用 SQLite `mode=ro` 读取 `memories_1.sqlite`、`memories_v2_1.sqlite`：先读 schema，再统计提取记录。两套记录数可能重叠且格式不同，不能相加当作独立记忆总数，也不能凭数量判断是否完整迁移。
3. 检查 `[features].memories` 与 `[memories]` 的 `version`、`use_memories`、`generate_memories`，以及可能的启动覆盖。文件存在只证明数据保留；配置只证明选择意图；新聊天实际注入的摘要及读取指令才是使用中的证据。
4. 不根据文件夹名或摘要首行的 `v1` 推断运行版本。`memories_v2/memory_summary.md` 的文本也可能以 `v1` 开头。若无法观察实际注入，明确标为“配置已设置，运行时尚未验证”。

## 使用正式版本开关

在支持该配置的客户端中，`[memories].version` 选择整套记忆管线：

| 配置值 | 生成文件目录 |
| --- | --- |
| `"v1"` | `memories` |
| `"v2"` | `memories_v2` |

执行前核实已安装版本支持该字段。可查配置 schema 或匹配版本源码中的 `MemoriesToml.version`、`MemoryVersion::directory_name()`；本地源码可能落后于安装版本，不能只凭源码下结论。客户端支持时，使用其 `app-server --print-startup-config` 做配置校验。不要把未显式设置版本解释为固定默认值：默认选择可能受版本、既有配置和迁移逻辑影响。

用户明确要求切回旧目录时：

1. 将当前 `config.toml` 备份到本机私有恢复目录。编辑前重新读取，只修改目标字段，避免覆盖同时发生的改动；不输出无关配置或凭据。
2. 在现有 `[memories]` 中新增或更新 `version = "v1"`，不得重复创建同名表或键。用户要求切换到新版时对应设置 `"v2"`。
3. 保留其他配置。`use_memories` 控制是否使用记忆，`generate_memories` 控制生成；如果它们原先关闭，说明这对切换的影响，不因选择版本就擅自启用。已有开关均为 true 时，结果示例：

   ```toml
   [memories]
   version = "v1"
   generate_memories = true
   use_memories = true
   ```

4. 保留两套目录和数据库，不改名、不建替代符号链接、不复制数据库覆盖，也不将 v2 的生成文件覆盖进 v1。不要顺带改变 `dual_write`：支持它的版本可能在使用 v1 时同时生成两套记忆；选择 v1 不必然意味着 v2 停止更新。
5. 使用实际客户端二进制校验配置；只输出校验结果和本次修改字段，避免直接展示整份启动配置。校验失败时修正本次改动，不能报告切换成功。若需撤销，恢复原来的 `version` 值；原先未设置则删除新增键，保留后续其他改动。

## 生效与验证

- 告知用户重启客户端后新建聊天验证；当前聊天已经注入的摘要不会因修改磁盘配置而替换。只有用户授权重启且已协调运行任务时才代为重启，不默认打断工作。
- 在新聊天核对实际记忆指令引用的目录及摘要来源。不要为了让旧聊天“看起来生效”而手动读取文件后宣称自动加载已经切换。
- 报告配置设置、客户端校验、运行时验证三个阶段的实际状态。旧记录还在与旧记录会自动生效是不同结论。
- 若用户要求将两套记忆合并，另行比较来源、时间和冲突后制定迁移方案；本流程没有验证跨版本内容转换，不能把选择 `version` 当成内容迁移完成。

已观察到的案例：两套目录和数据库均存在，当前聊天注入 v2 摘要；添加 `version = "v1"` 后，安装客户端的配置校验通过。该证据仅证明开关被接受，不单独证明重启后新聊天已使用 v1，也不证明两套历史记录已完整互迁。
