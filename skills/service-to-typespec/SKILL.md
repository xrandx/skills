# 从代码理解服务并生成契约

以当前实现为依据，说明服务接口及其业务行为，生成可追溯、可重新构建的契约。只修改契约、说明和必要的共享工具链；只要求修改 skill 时，不启动生成。

## 输入与分工

接受三个参数：`source_dir`（源码目录）、`output_dir`（TypeSpec 源码与共享工具链目录）、可选 `services`（服务名单，默认全部）。路径可从本次对话取得；必需路径缺失时询问，不固定使用某个仓库目录。相对路径按当前项目根目录解析，服务名单在源码目录内匹配。

从实际启动、路由和消息入口识别服务，不限于已有契约的目录。多个服务默认各由一个独立 subagent 处理，在可用并发额度内执行；单服务或不支持 subagent 时串行处理。

- 主 agent：盘点范围，准备共享工具链，维护公共文件与类型，汇总并验收。
- subagent：独立取证、建模和验证，只写自己服务的目录及对应集中输出；返回文件、覆盖数量、缺口、命令与结果。共享变更交给主 agent。
- 委派时提供源码与输出路径、已有修改、本 skill 和共享命令。同一服务同时只有一个写入者；无法隔离写入的构建由主 agent 串行执行。

## Review

用户指定 commit id 或源码文件夹要求 review 时，先只读审查，不执行生成与更新：

- commit：比较该提交与第一父提交的变化（根提交视为新增），读取相关完整实现，对照当前 TypeSpec；说明比较基线，核对后续代码变化，避免把已失效的历史行为同步回来。
- 文件夹：对照该目录当前代码与对应 TypeSpec，必要时追踪外部挂载和共享类型；同时指定 commit 和目录时，以目录限定提交范围。
- 按下述取证要求检查接口、字段、消息及中文行为描述，列出代码与 TypeSpec 位置、已确认差距和建议修改；证据不足单独说明，无差距则如实报告。多服务可委派只读 subagent。
- 有差距时先展示拟修改范围，再询问用户是否修改 TypeSpec；等待确认后才按生成与验收流程处理获准内容。已有明确授权覆盖这些修改时不重复确认。确认前不修改契约、说明或生成产物。

## 取证与描述

追踪 HTTP 的挂载、鉴权、路由、校验、业务逻辑、序列化及错误；追踪跨边界消息的生产/消费、通道、方向、编码、负载和投递。旧文档、测试与自动生成的 schema 只用于交叉核对。

覆盖业务、内部、健康探针及流式接口；排除项说明依据。内部回调、后台任务或 HTTP 202 不自动构成消息接口。核对请求/响应、状态码、字段约束、认证与错误，以及状态变化、副作用、接受与完成、幂等和重试；消息还要核对心跳、终止、顺序、确认与重放。

每个 HTTP 和消息 operation 同时写中文 `@summary`（一句话功能）与 `@doc`（行为、条件、失败和完成边界）。模型、消息及非显然字段用 `@doc` 解释。内部调用链用于取证，不要求另写实现原理文档。

## 生成与更新

生成前读取 [产物规范](references/output-standard.md)。按业务领域组织 TypeSpec，保留真实协议名称和已有 operationId；共享语义一致的类型，不机械照搬源码目录或数据库表。

- 已有契约按当前实现增量更新，保留准确描述、组织方式和用户修改；确认接口已变更或删除后同步调整。
- 全部服务共用依赖、锁文件和脚本，不在服务目录创建 package.json、锁文件或 node_modules；沿用兼容工具链。
- 有 HTTP 接口即导出 OpenAPI，有跨边界消息即导出 AsyncAPI。不适用的格式在 README 说明原因，不生成空占位文档。
- 局部未查清时完成已确认部分，在 README 列出缺口，不猜测或用宽泛类型掩盖。工具不支持属于未完成，不等于协议不存在；只有影响整体范围或建模方向的歧义才询问用户。

### 转换工具

可参考已有项目的组合：`@typespec/compiler`、`@typespec/http`、`@typespec/openapi`、`@typespec/openapi3` 均为 `1.16.0`，`tsp-asyncapi` 为 `0.7.2`，`@asyncapi/parser` 为 `3.6.3`。版本仅作参考，优先复用目标项目兼容的锁定依赖。

- OpenAPI：编译 `main.tsp`，由 `@typespec/openapi3` 导出 YAML；用项目的 OpenAPI parser（如 `@scalar/openapi-parser`）校验。
- AsyncAPI：编译 `asyncapi.tsp`，通过独立配置选择社区 emitter `tsp-asyncapi` 导出 YAML；用 `@asyncapi/parser` 校验，并核对消息 payload。
- 共享脚本将 YAML 输出到 `output_dir` 同级的 `openapi/`、`asyncapi/`，文件名为 `<服务名>.openapi.yaml`、`<服务名>.asyncapi.yaml`；用户指定其他产物路径时遵从其配置。两类产物只生成 YAML，各产物目录用自己的 `.gitignore` 忽略 `*.yaml`、`*.yml`，保留 README 和预览页面。已有同名 npm scripts 时，可用下列命令；缺失时先补齐共享脚本，不把示例当成 TypeSpec 内置命令。

```bash
npm run build --prefix "<output_dir>"                         # 全量
npm run build --prefix "<output_dir>" -- <服务名>             # 指定服务
npm run build:openapi --prefix "<output_dir>" -- <服务名>
npm run build:asyncapi --prefix "<output_dir>" -- <服务名>
npm run verify --prefix "<output_dir>"                        # 全量校验
npm run verify:asyncapi --prefix "<output_dir>" -- <服务名>
```

替换目录与服务名后执行；workspace 使用其实际包管理器命令。构建不等于完整校验，验证步骤须明确执行；服务发现应兼容仅有消息入口的服务。

## 验收与交付

主 agent 对照实际文件验收，不能只采信 subagent 的完成报告：

1. 发现的服务和接口与建模覆盖对应，适用的导出完整；排除及缺口有说明。
2. 格式化、编译和对应版本的 OpenAPI/AsyncAPI 校验通过，引用有效，中文摘要与详细说明保留。
3. 请求/响应、状态码、鉴权、消息方向及约束与代码一致；共用 payload 在不同产物中保持一致。
4. 简短 README 能引导阅读、定位关键源码、解释业务行为，并提供可复现命令及实际验证结果。
5. 修改导出路径或预览页面时，保留并同步已有预览说明；在两个适用的产物目录分别运行 `npx --yes serve .`，用浏览器打开实际 Local 地址，检查文档加载、中文说明和服务切换。只记录实际验证的服务，结束后停止自己启动的测试进程。

共享类型或工具链变更后重验受影响服务。失败服务不阻塞其他服务，旧产物不能计为本次成功。最终提供产物链接、服务覆盖数量、验证结果和缺口，区分完成、不适用与未完成。默认不调用真实业务接口或订阅线上事件流，不将静态验证表述为运行时验证。
